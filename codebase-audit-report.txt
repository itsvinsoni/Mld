1. EXECUTIVE SUMMARY
====================================================================

MLD Memorial Sansthan ka current project ek React + TypeScript + Vite single-page application hai. Ismein do major experiences hain: public-facing education website aur /admin route ke andar ek CRM-style management dashboard. Public website mein home page, institutions listing, institution detail pages, programme/course detail pages, about, gallery, messages aur contact pages hain. CRM side mein dashboard, students, fees, colleges, courses, faculty, library, reports aur settings views diye gaye hain.

Compilation level par project healthy hai. Production build successfully complete hua, TypeScript noEmit check pass hua, npm audit mein vulnerabilities nahi miliं, Vite development server ne root aur deep route dono serve kiye, aur programme slugs duplicate nahi mile. Iska matlab basic syntax, module resolution aur build pipeline workable hai.

Lekin build pass hona production readiness ka proof nahi hai. Detailed review mein kai user-facing aur security-related problems miliं. Sabse important issue admin login ka hai: login logic email ko check karta hai, password ko ignore karta hai. Isliye kisi valid demo email ke saath arbitrary password use karke access mil sakta hai. Agar is dashboard ko real CRM samjha ja raha hai to ye release-blocking security defect hai.

Doosra major issue routing migration ka hai. Current application clean History API routes use karti hai, jaise /contact aur /admin. Lekin public institution data ke kai action links abhi purane hash format #/contact aur #/admin par hain. Current router un links ko intercept nahi karta. Is wajah se Admission Enquiry aur ERP Login buttons expected page par navigate nahi karte.

Teesra major issue contact form ka hai. User form fill karke submit karta hai, application sirf local submitted state set karti hai aur success message dikha deti hai. Form data kisi API, email service, database, Netlify form ya external form endpoint ko send nahi hota. Iska matlab visitor ko false confirmation milti hai ki message receive ho gaya, jabki institution ko message milta hi nahi.

CRM dashboard ke Add, Edit, View, Receipt aur settings controls largely visual placeholders hain. Buttons render hote hain lekin handlers ya persistence nahi hai. Agar product ko demo/prototype ke roop mein present kiya ja raha hai to ye acceptable ho sakta hai, lekin “management dashboard” ya “CRM” ke roop mein deploy karna misleading hoga.

Kuch external links invalid ya placeholder hain. Pharmacy page ka Visit Web Page link # hai, aur livestock page ka link relative ASPX filename hai jiska current domain par valid destination hone ka evidence nahi hai. Public data aur Hindi/English statistics mein bhi inconsistencies hain. Images external site se hot-link hoti hain, jisse availability aur performance ka operational risk hai.

Final verdict: Project compile-ready hai, demo-ready hai, lekin production-ready nahi. Public website ke visual portions strong hain, routing aur deployment foundation workable hai, par security, form delivery, functional CRM scope, link cleanup aur content/data consistency fix kiye bina release nahi karna chahiye.

6. DETAILED FINDING 1: PASSWORD VERIFICATION MISSING
====================================================================

Severity: HIGH / P1. If deployed as real CRM: RELEASE BLOCKER.

Files:
- App.tsx, lines 61-70.
- components/Login.tsx, lines 15-20 and password input area.
- constants.ts, MOCK_USERS.

Observed behavior:

App.tsx ka `handleLogin` function email se user find karta hai. `pass` parameter receive hota hai, lekin use nahi kiya jata. User milte hi `setCurrentUser(user)` call hota hai. Login form user ke entered password ko bhi pass nahi karta; hardcoded `'demo123'` pass hota hai.

Impact:

Agar kisi ko valid email address pata hai, to koi bhi password enter karke access mil sakta hai. Password field sirf visual input hai. Ye authentication bypass hai. Demo account email addresses source code mein visible hain, isliye unauthorized visitor ke liye valid identity guess karna trivial hai.

Additional concern:

CurrentUser sirf React memory state mein hai. Browser refresh par state reset hoti hai, lekin isse security problem solve nahi hoti. Real authorization backend par honi chahiye. UI mein role-based menu hide karna access control nahi hai; malicious user browser code modify karke hidden view render kar sakta hai.

Recommended correction:

Demo mode explicitly document karein ya real auth implement karein.

Real implementation ke liye:

1. Login request backend endpoint par bhejein.
2. Password backend par salted hash ke against verify ho.
3. Password kabhi frontend constants ya source code mein na rakhein.
4. Successful login par secure, HttpOnly, SameSite cookie-based session prefer karein.
5. Backend har protected API request par role authorization check kare.
6. Frontend sirf UX-level role filtering kare.
7. Login failures generic message dikhayein.
8. Rate limiting, lockout aur audit logging add karein.
9. Logout server-side session invalidate kare.
10. Session expiry aur refresh handling add karein.

Temporary demo-only correction:

Agar app intentionally demo hai, to login page par prominent “Demo dashboard — no real data or authentication” notice dikhayein. Phir bhi arbitrary password acceptance ko intentionally code comment aur README mein clearly document karein. Public production domain par demo credentials expose karna avoid karein.

Acceptance criteria:

- Wrong password se login fail.
- Correct password se login success.
- Direct protected API call without session fail.
- Role mismatch se unauthorized operation fail.
- Refresh ke baad session policy expected behavior follow kare.

All internal action hrefs ko clean routes mein replace karein:

- `#/contact` -> `/contact`
- `#/admin` -> `/admin`

Legacy compatibility ke liye agar old URLs externally used hain to router mein hash migration logic add kar sakte hain, lekin data ko new canonical URLs par migrate karna primary fix hai.

Additional route design recommendation:

`Link` component ko internal navigation ke liye consistently use karein, ya global interceptor ko robustly test karein. Har internal anchor ko raw `<a>` rakhne se behavior duplicate sources mein spread hota hai. Agar raw anchors intentionally use kiye gaye hain, to route contract documented hona chahiye.

Acceptance criteria:

====================================================================

Severity: HIGH / P1 if contact capture business requirement hai.

“Your message has been received. We'll be in touch soon.”

Ye text actual delivery ke bina show hota hai.

Impact:

Visitor apna naam, phone, email aur message enter karta hai. UI success show hone ke baad data lost ho jata hai. Institution ko enquiry nahi milti. Admissions lead lost ho sakti hai. User trust damage hota hai.

Recommended implementation options:

Option A: Backend API.

- Controlled fields state mein rakhein.
- Client validation karein.
- HTTPS POST `/api/contact` endpoint call karein.
- Server-side validation aur spam protection karein.
- Server email/CRM/database integration kare.
- API success ke baad hi success UI show karein.
- Failure par retryable error show karein.

Option B: Netlify Forms.

- Form ko correct `name` attribute aur Netlify form attributes dein.
- Production deploy par Netlify dashboard mein submissions monitor karein.
- Hidden honeypot field add karein.
- Success redirect ya local success state only after confirmed submission use karein.

Option C: Third-party form provider.

- Formspree ya trusted provider ka endpoint use karein.
- Privacy policy aur data processor disclosure add karein.
- Client-side validation ke saath server response check karein.

Option D: Temporary mailto fallback.

- User ke data se `mailto:` URL generate karein.
- Is approach ki browser/email-client dependency explain karein.
- “Your email client will open” jaisa accurate message dikhayein, false received message nahi.

Required safeguards:

- Required inputs ke labels aur name attributes.
- Phone format validation.
- Maximum message length.
- Rate limiting.
- Honeypot/CAPTCHA as required.
- XSS-safe rendering.
- PII handling policy.
- Success and failure analytics without storing sensitive content unnecessarily.

Acceptance criteria:

- Form submit hone par actual network request ya configured provider submission ho.
- Server success ke bina success message na aaye.
- Network failure mein data loss risk ke baare mein user ko clear message mile.
- Duplicate submit prevention ho.
- Loading state aur disabled submit button ho.
- Submission test staging environment mein verify ho.

25. PROPOSED IMPLEMENTATION DETAILS
====================================================================

25.1 Clean internal route migration

A simple first patch should update action definitions in pages/data.ts. Internal links must be canonical path strings. The external boolean must remain false for internal paths. InstitutionDetailPage already uses target only when external is true, so this change is low risk.

After patch:

- Admission Enquiry: `/contact`
- ERP Login: `/admin`

Then add a test that renders institution action buttons and asserts the href values.

25.2 Login contract

Current callback signature `onLogin(email, pass)` is a useful starting point, but password should be passed from LoginScreen:

- `onLogin(email, password)`
- App or auth service validates credentials.
- Do not hardcode a password in component.

For real deployment, callback should become async and return a structured result:

- `{ ok: true, user }`
- `{ ok: false, code: 'INVALID_CREDENTIALS' }`

Loading state and error state should be separated. Avoid revealing whether email exists.

25.3 Contact form contract

Define a ContactEnquiry type:

- name
- phone
- email
- interest
- message
- sourcePage
- optional programmeSlug

Use controlled state or FormData. Submit to a typed API. Disable button while submitting. Reset only after confirmed success. Use an accessible status region.

25.4 Admin state

Avoid passing large mock arrays directly from App.tsx once backend exists. Use query hooks or service modules. Keep server state separate from UI state. Add cache invalidation after mutations. Derive permissions from a centralized policy map rather than repeating arrays in every view.

25.5 Route abstraction

Use a route object with:

- pathname
- searchParams
- hash
- segments

Hash migration can inspect initial `window.location.hash` and replace old `#/path` URLs, but canonical links must still be updated.
